1The big picture

Data comes in on the top row. Questions go out on the bottom row. MongoDB sits in the middle and holds everything in one collection called qa_knowledge.

Figure 1 — Ingest on top, ask on the bottom. The LLM never touches MongoDB directly; it only uses MCP tools.

The one idea to remember

Markdown = what the LLM reads

Clean text with title, steps and expected result. The LLM can quote it word for word.

Vector = how we find by meaning

A list of numbers made from the Markdown. Similar meaning gives similar numbers.

Fields + links = exact facts

Status, owner, module and relations[] give exact filters and connections.
All three live in the same JSON document. One search can filter by fields, rank by meaning, and then follow links.

2Three ways to find things

Users ask different kinds of questions. Each kind needs a different search. The LLM picks the right one, or combines them.

🔑 Keyword search

Finds exact words: codes, IDs and names.

"Show test INT-RxFill-Naproxen-2a"
"Tests for ADT-A08"

MongoDB: $search (Atlas Search)

🧠 Semantic search

Finds same meaning, even when the words are different.

"What if the pharmacy can't give the full quantity?"
→ finds the "Partially Dispensed / Out of Stock" test

MongoDB: $vectorSearch

🔗 Relationship search

Follows links between docs: test → bug → code.

"This test failed. Which Jira bug and which code file are related?"

MongoDB: $graphLookup

Plus two helpers

⚡ Hybrid = keyword + semantic together

Both searches run, and their result lists are merged with $rankFusion (MongoDB 8.1+). This is best when a question has a code and an idea: "ADT-A08 insurance update test in env 93".

📊 Stats = counting

Plain aggregate() with $group. No vectors needed. "How many MySQL tests failed per module?"

Which search for which question?

If the question…UseExample

3The JSON format (5 document types)

There is one collection with a doc_type field. Every type shares the same "common part", so one search covers everything.

test_case

one Excel test row

feature

eRx, ADT, eFax…

context

test data, config, preconditions

jira_ticket

one bug or story

code_chunk

one function or class

The common part (every document has these)

FieldWhat it is for
_idA stable, readable ID such as TC:INTEROP:eRx:R27. Links point to it.
doc_typeSays which of the 5 types this is, so searches can filter by type.
sourceWhere it came from: sheet and row, Jira key, or file path. Used for citations.
hierarchy.breadcrumbWhere it lives, e.g. Interop > eRx > Testcase - 1 > CancelRx.
entities[]Typed "things" mentioned (patient, drug, HL7 message, file). These join docs across sources.
relations[]Arrows to other docs: BELONGS_TO, DEPENDS_ON, AFFECTS, FIXED_BY…
search.keywordsExact words for keyword search, including spelling variants found in the sheets.
content_mdClean Markdown. This is what the LLM reads and what gets embedded.
embeddingThe vector plus a hash of the text, so we re-embed only when the text changes.

4How everything links

Each arrow is one entry in a document's relations[]. Once these arrows exist, the LLM can walk from a failed test to the bug and then to the code.

Figure 2 — A small slice of the graph. Real data: TC R26/R27/R57 and Testcase - 1. Jira and code nodes are examples.

How the links are made (automatically)

LinkRuleExample
BELONGS_TOSheet name or Jira component matches a featuresheet "eRx" → FEAT:eRx
USES_CONTEXTRow sits under a parent block or precondition rowR27 is under "Testcase - 1"
DEPENDS_ONWithin a group, "Validate X" follows "Send X"R27 depends on R26
SAME_SCENARIOSame title in another group (different test data)R27 ↔ R57
AFFECTSJira mentions a TC id or title, or QA links itOPI-2045 → R27
FIXED_BYA commit message contains the Jira key; changed functions get the link"OPI-2045 fix denial code"
IMPLEMENTS / TESTED_BYCode and tests share the same entity (e.g. message type CancelRxResponse)Parser ↔ R27
Shared entities are the "glue". Patient 118 appears in eRx and ePA. CancelRxResponse appears in a test, a ticket and a code file. One query on entities.value finds all of them.

5Building the data (pipeline)

One script per source. They all write the same JSON shape into the same collection.

Figure 3 — Three input lanes feed the same common steps.

Storing Jira tickets: simple rules

  • One document per ticket. Summary, description and a short comment summary go in content_md.
  • Status, priority, assignee and fix version are fields, not embedded text.
  • Fetch only tickets updated since the last run (JQL updated >= -1d).
  • If a comment thread is very long, split it into a second chunk with the same source.key.

Storing source code: simple rules

  • One document per function or class. Never cut code in the middle of a function.
  • Add a plain-English summary written by the LLM. Questions are in English, so the summary helps semantic search a lot.
  • Store commit and lines so answers can point to file:line.
  • Re-index only files changed in each merge. Remove docs for deleted files.

7MCP tools design

The MCP server is a small program between the LLM and MongoDB. It offers a few clear, read-only tools. The LLM chooses which tool to call and with what inputs.

ToolInputsRuns in MongoDBUse it for
search_knowledgequery, mode (keyword / semantic / hybrid), doc_types, filters, limit$search · $vectorSearch · $rankFusionFinding anything by words or meaning
get_documentid, include (context, feature, runs)find + $lookupReading one doc in full, with its parent context
filter_test_casesmodule, section, status, track, owner, environmentfind()Exact lists ("Marcelo's MySQL fails")
find_relatedid, relation_types, depth (max 3)$graphLookup"What is connected to this?"
find_by_entitytype, valuefind on entitiesEverything about patient 118 or ADT_A08
get_statsgroup_by, filtersaggregate $groupCounts and pass rates
trace_issuestart_id (TC id or Jira key)several of the aboveOne-shot bundle: test + bug + code + context
MCP TOOL SCHEMA What the LLM sees for search_knowledge
{
  "name": "search_knowledge",
  "description": "Search test cases, features, context, Jira tickets and code. Use mode 'keyword' for IDs, codes and exact names; 'semantic' for questions in normal words; 'hybrid' when the question has both. Returns short Markdown snippets with ids for citation.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query":     { "type": "string" },
      "mode":      { "type": "string", "enum": ["keyword", "semantic", "hybrid"], "default": "hybrid" },
      "doc_types": { "type": "array", "items": { "enum": ["test_case", "feature", "context", "jira_ticket", "code_chunk"] } },
      "filters": {
        "type": "object",
        "properties": {
          "module":      { "type": "string" },
          "environment": { "type": "string" },
          "status":      { "enum": ["PASS", "FAIL", "BLOCKED", "NA", "NOT_RUN"] },
          "track":       { "enum": ["Firebird", "MySQL", "default"] }
        }
      },
      "limit": { "type": "integer", "default": 8, "maximum": 20 }
    },
    "required": ["query"]
  }
}
What a tool returns (small and easy to cite)
{
  "results": [
    { "id": "TC:INTEROP:eRx:R39", "doc_type": "test_case", "score": 0.91,
      "breadcrumb": "Interop > eRx > Testcase - 2 > RxFill",
      "title": "Send - RxFill request to OP - 2a",
      "snippet_md": "...Status is **Partially Dispensed** ... Reason Code is **Out of Stock**...",
      "latest_status": { "track": "default", "status": "PASS" },
      "cite": "InteropsTeamFunctionalityDetails › eRx › row 39" }
  ],
  "next_hint": "Call get_document(id) for full steps, or find_related(id) for links."
}
Design rules for the tools
  • Few tools with clear names. The descriptions tell the LLM when to use each one.
  • Never return vectors. Return ids, breadcrumbs, short Markdown and a cite string.
  • Limit the size (default 8 results, graph depth at most 3) so the LLM's context stays clean.
  • Enums for filters. The LLM can't invent a status like "Passed!!".
  • Read-only. The tools never write to the database.

🔗 Demo 4 · Complex relationship questionmulti-hop: test → bug → code
"Why is the CancelRx response validation failing, and which code should a developer look at?"
filter_test_cases(module: eRx, status: FAIL, keyword: CancelRx)finds R27find_related(R27, depth 2)gets R26, Jira, codeget_document for eachexplain
db.qa_knowledge.aggregate([
  { $match: { _id: "TC:INTEROP:eRx:R27" } },
  { $graphLookup: { from: "qa_knowledge", startWith: "$relations.target",
      connectFromField: "relations.target", connectToField: "_id",
      as: "linked", maxDepth: 1, depthField: "hop" } },
  { $project: { "linked._id": 1, "linked.doc_type": 1, "linked.title": 1, "linked.summary": 1,
                "linked.runs": 1, "linked.status": 1, "linked.hop": 1 } }
])
// Jira tickets point TO the test (AFFECTS), so also run:
db.qa_knowledge.find({ "relations.target": "TC:INTEROP:eRx:R27", doc_type: "jira_ticket" })
Answer (the LLM joins the dots):
  1. The failing test: eRx row 27 checks that the CancelResponse XML has Denial Reason, Code and Type. It is FAIL.
  2. The step before it: row 26 sends that CancelResponse. It is marked Pass, but its comment says "Canel - Pending", so the send may not have completed. ⚠️ The data looks inconsistent.
  3. Same check, other data: row 57 (patient 123) has comment "cancel pending". That suggests the problem isn't tied to one patient.
  4. Known bug: OPI-2045 (example), "Denial Reason Code missing", is In Progress.
  5. Where to look: CancelRxResponseParser.Parse, src/Surescripts/CancelRxResponseParser.cs lines 42–118 (example).

📊 Demo 5 · Stats questioncounting, no vectors
"Which module has the most MySQL failures right now?"
Counting → statsget_stats(group_by: module, track: MySQL, status: FAIL)answer with a small table
db.qa_knowledge.aggregate([
  { $match: { doc_type: "test_case" } },
  { $set:   { latest: { $last: { $filter: { input: "$runs", cond: { $eq: ["$$this.track", "MySQL"] } } } } } },
  { $match: { "latest.status": "FAIL" } },
  { $group: { _id: "$hierarchy.module", fails: { $sum: 1 } } },
  { $sort:  { fails: -1 } }
])
Answer: A ranked list such as "Billing 12, FrontDesk 7, Nurse 3…", with a link to see the failing tests in each module. (The numbers depend on live data. Your current sheets are mostly NOT_RUN.)

10Why this helps the LLM find solutions and explain

Compare a plain "Excel rows as text" setup with this design, for the same question as Demo 4.

❌ Without this design

  • The search finds row 27 alone. It doesn't know the patient or the drug, because that data was in row 2.
  • It has no idea that row 26 must run first.
  • It can't see the Jira bug or the code.
  • "Pass" vs "pass " vs "Fail" can't be filtered reliably.
  • The LLM guesses, and may make up a cause.

✅ With this design

  • context_snapshot means every chunk knows its patient, drug and pharmacy.
  • DEPENDS_ON means the LLM checks the step before.
  • AFFECTS / FIXED_BY means the bug and the code are one hop away.
  • Clean status enums mean exact filters and counts.
  • Citations mean every claim points to a row, ticket or file. The LLM explains instead of guessing.

11Step-by-step rollout

Build it in small steps. Each step is useful on its own.

Step 1
Excel → MongoDB. Column mapping, sections, parent blocks, clean statuses, runs[], content_md, embeddings. Create the 3 indexes.
Done when: all ≈2,770 + interop tests are loaded, and a spot-check of 20 rows matches Excel.
Step 2
MCP server (read-only) with search_knowledge, get_document, filter_test_cases and get_stats.
Done when: Demos 1, 2, 3 and 5 work end to end.
Step 3
Links inside test data: BELONGS_TO, USES_CONTEXT, DEPENDS_ON, SAME_SCENARIO, plus the find_related and find_by_entity tools.
Done when: "what depends on R26?" returns R27.
Step 4
Jira: sync tickets updated since the last run, summarize comments, and create AFFECTS links.
Done when: each failed test shows its linked bug.
Step 5
Source code: function-level chunks, LLM summaries, FIXED_BY links from commit messages, plus the trace_issue tool.
Done when: Demo 4 works end to end with real data.
Step 6
Measure quality. Write 50 real questions with known right answers. Check that the right doc is in the top 5 and that every claim has a source. Tune keywords, aliases and weights.

12Notes & limits

  • Dates: the Excel sheets have no "tested on" column, so executed_at stays empty until testers add one. recorded_at is set by the import.
  • Jira and code examples in this document (OPI-2045, CancelRxResponseParser) are made up to show the flow. Replace them with real ones.
  • MongoDB version: $vectorSearch and $search run on Atlas, or self-hosted with the search process (mongot). $rankFusion needs 8.1+. Check your exact version first.
  • Embedding model: pick one and keep it. Changing models means re-embedding everything. Store the model name in embedding.model.
  • Security: the test data has patient names. Keep the MCP server read-only, behind login, and restrict who can query it.
